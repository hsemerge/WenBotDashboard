# WenBot System Audit — Security + Firestore Cost

**Date:** 20 Aug 2026
**Scope:** GiveawayBot (Netlify functions, Firestore rules, dashboard, portals, overlays) + WenBotServer (Railway bot loops)
**Method:** Read-only. Mapped all 104 Netlify functions, the 428-line Firestore ruleset, every recurring server loop, and every overlay poll. No code changed.

This is an analysis deliverable — nothing here has been applied. Each item lists the fix and, where relevant, the estimated cost impact, so it can be turned into work in priority order.

---

## TL;DR

- **Security posture is good.** No open holes that leak secrets or let a client escalate. Firestore rules are default-deny with a thorough denylist; economy endpoints all bind identity and use transactions. Two *real but bounded* weaknesses (Discord-verify can certify unlimited accounts; casino-verify gate accepts "verified" without "under code") — both are design choices worth revisiting, not bugs.
- **The Firestore cost is almost entirely READS, and one loop dominates.** `loadVerifiedUsers` re-reads a streamer's entire `verified_users` collection every 2 minutes, for every running bot, whether anything changed or not. That single loop plausibly accounts for the majority of the 2.7M reads/day. Converting it to a snapshot listener (like the three sibling loaders already are) is the highest-leverage change available.
- **Overlays are the second driver.** Several overlay endpoints poll every 300–1500ms with NO server-side cache, doing a fresh streamer lookup + document read on every tick.
- **Writes** are inflated by a per-bot 60-second heartbeat (~65k writes/day across the fleet for "I'm alive").

Fixing the top 3 read items and the heartbeat should cut the bill substantially without changing any user-visible behaviour.

## PART 1 — SECURITY

### 1.1 What's solid (verified, no action)

- **Firestore rules**: default-deny catch-all; `system/`, `giveaway_fairness/`, `share_links/`, `draw_codes/`, `discord_verify_tokens/`, `admin_audit_logs/` all admin-SDK-only. Streamer-doc create/update carry an explicit denylist blocking self-set of `plan`, `stripe*`, `kick*`, `modUids`, `email`, trial/referral fields. Mods can't escalate.
- **Admin endpoints** (16): all gated on `requireAdmin` + rate limit + method guard. The one named-but-different case, `admin-slots-ingest`, correctly uses a timing-safe shared key (it's called cross-origin from a stake.com bookmarklet, so a Firebase token can't reach it).
- **Shared-key endpoints** (`kick-store-wenbot`, `discord-register-commands`) use `timingSafeEq`, not `==`.
- **Economy endpoints** (`store-buy`, `wenpoints-spend/box/checkin`, `portal-daily-claim`): every one re-verifies the Kick token AND checks the resolved username matches the claimed one ("Identity mismatch") before any balance change, and every mutation is inside a `runTransaction`. No spoofing, no double-spend.
- **Scoped share links** (`share.js`): identical response for wrong/revoked/expired tokens (no oracle), never returns the raw profile, scope-limited views only.
- **Draw fairness**: seeds are admin-SDK-only and reach the public solely through `/api/draw-proof` after the committed draw — the streamer cannot see a seed before entries open.
- **No secrets committed.** Only the Firebase Web API key (`js/firebase-config.js`) is in the repo, which is correct — it's a public client identifier, not a secret, and Firestore rules are the actual guard.

### 1.2 Weakness — Discord-verify can certify unlimited Kick accounts  (MEDIUM)

`discord_links` is keyed by Discord user ID, so re-linking to a second Kick name **moves** the link rather than refusing it. But `discordVerified` is stamped onto the *first* account's `verified_users` record and **nothing ever clears it** (grep confirms no writer sets it false). So account A keeps its Discord-verified badge after the Discord moves to B, and both pass a "Discord Verified" giveaway gate.

- **Impact:** one Discord can certify any number of Kick accounts, one after another. Only bites streamers who gate giveaways on Discord-verify *alone*.
- **Fix:** when `saveDiscordLink` moves a Discord to a new Kick name, clear `discordVerified` on the previous holder's records. ~15 lines in `_lib/discord-link.js`.

### 1.3 Weakness — casino-verify gate accepts "verified" without "under code"  (MEDIUM, partly by design)

The giveaway gate `verifiedCasino` checks a verification record *exists* (`p !== "none"`), not that `underAffiliate` is true. And for the honour-system casinos (everything except Gambulls/Rainbet/Duelbits/Clash) the casino username is taken at face value with no API check.

- **Impact:** on an honour-system casino (e.g. Degen, CSGOBig, Stake), someone with N Kick accounts can verify N invented casino names and pass a casino-verified gate N times. The only constraint is each casino name being unique on that channel.
- **Note:** this is softened right now because code-type giveaways are disabled by `GIVEAWAY_COMPLIANCE_HOLD`, so wager-weighting and code-only entry aren't running. With the hold on, "verified" is more an identity record than a multi-account defence.
- **Options:** (a) offer a stricter gate that requires `underAffiliate`; (b) block on the stable `providerUid` (already stored) as well as name, so a casino rename can't mint a fresh identity. `detectAnomalies` already *flags* both cases to mods — this would *enforce* them.

### 1.4 Data-exposure review (public read endpoints)

Checked every `NONE`-auth endpoint for what it returns. **No leaks found** — the public read endpoints (`portal-data`, `leaderboard-live`, `slot-request-data`, `gtb-guesses`, `store-public`, etc.) return only display data (masked casino names, slot names, public wager standings). `share.js` explicitly comments that it never returns the raw profile because "it carries Kick tokens, Stripe ids and every other setting" — and it doesn't. `discord-guild-info` returns only the server name/icon. Nothing exposes `kickAccessToken`, `apiKey`, `credential`, Stripe ids, or emails.

One thing to keep an eye on, not a finding: `viewer-wager` returns a viewer's own wager total — correctly bound to their Kick token, one number, never the board. Fine as-is.

## PART 2 — FIRESTORE COST

Observed: **~2.7M reads/day**, 321K writes/day, 8.8K deletes/day; project cost ~$38/mo (Blaze), driven by reads over the 50k/day free tier. Fleet is ~45 onboarded streamers.

### 2.1 #1 READ DRIVER — `loadVerifiedUsers` full re-read every 2 min  (HIGH)

`streamer-bot.js` sets up four per-bot data sources. Three are live `onSnapshot` listeners (`watchCommands`, `watchTimers`, `watchModeration`) — read once, then only deltas. The fourth, `loadVerifiedUsers`, is a **blind `.get()` of the entire `verified_users` subcollection every 2 minutes**, per running bot, whether or not anything changed.

**Estimated cost:** a streamer with ~60 verified users → 60 reads × 720 ticks/day = **43,200 reads/day per streamer** → ~1.9M/day across ~45 bots. This one loop plausibly *is* the majority of the 2.7M.

**Fix:** convert it to an `onSnapshot` listener, exactly like its three siblings. Reads collapse from "every doc every 2 min" to "every doc once, then only what changes." Biggest single win in the whole system, and it's a mechanical change to code that already has three working examples beside it. **Est. reduction: 1–2M reads/day.**

### 2.2 #2 READ DRIVER — uncached overlay polling  (HIGH)

Several overlay endpoints do `findStreamerByChannel` (1–2 reads) + a data `.get()` (1+ reads) on **every poll, with no `_cache`**:

| Overlay | Poll rate | Endpoint | Server cache? |
|---|---|---|---|
| bonus-hunt | **800ms** | `bonus-hunt-data` | none |
| wheel / winner | **300ms** | `overlay-data` | none |
| bankroll / deposits / withdrawals / P&L | 1500ms | `bankroll-data` | none |
| giveaway | 1500ms | `overlay-data` | none |
| slot-requests | ~poll | `slot-request-data` (reads up to 50 docs) | none |
| banner | 1000ms | `portal-data` | **yes (150s)** ✅ |

A bonus-hunt overlay left open for an 8-hour stream at 800ms ≈ **72,000 reads** for that one overlay. Bankroll-family overlays are commonly left open all stream; a streamer running 4 of them = ~19k reads/hour.

**Fixes (two independent levers):**
1. **Add a short server-side `_cache` (2–5s) to `bonus-hunt-data`, `bankroll-data`, `slot-request-data`, `overlay-data`** — the same pattern `portal-data` already uses. A 3s cache on an 800ms poll cuts its reads ~4x with no visible lag.
2. **Slow the poll rates.** 300ms (wheel/winner) and 800ms (bonus-hunt) are far faster than the eye needs; 1000–1500ms is invisible on a stream overlay. The spinners only need fast polling during the brief reveal, not continuously.

### 2.3 #3 READ DRIVER — community rebuild every 2 min  (MEDIUM)

`community.js` `rebuildCreatorsDoc` runs every 2 min and reads **all** `onboarded == true` streamers (~45 docs) → ~32k reads/day. The Creators directory does not change second-to-second.
**Fix:** back the interval off to 5–10 min. `AGG_MS` 2min → 10min = 5x fewer. **Est. reduction: ~26k reads/day.**

### 2.4 WRITE DRIVER — 60-second heartbeat  (MEDIUM)

`_writeBotStatus` writes a `bot_status/current` heartbeat every 60s per bot → **~65k writes/day** across the fleet, purely for liveness.
**Fix:** every 3–5 min is plenty for a "stuck bot" signal (the stuck detector already tolerates minutes). 60s → 4min = ~4x fewer heartbeat writes. **Est. reduction: ~48k writes/day.**

### 2.5 Smaller items

- **`points` flush every 30s** (`SAVE_INTERVAL`): fine — it's buffered and only writes viewers with pending deltas. Leave it.
- **Giveaway snapshot every 5s** (`flushSnapshot`): only runs during an *active* giveaway, and the overlay needs it live. Leave it.
- **Scheduler loops every 5 min** (`bankCarryover`, `captureCheckpoints`): each queries `leaderboardPeriod.active == true` (~20 docs). ~12k reads/day combined. Low priority; could share a single query between the two instead of one each.
- **Storage bytes jump (35→50MB on Aug 20)** is the backup snapshots I uploaded to `gs://…/backups/` during today's rename work (full-snapshot 15.5MB + points snapshots). Storage is trivially under the 5GB free tier and is NOT a cost driver — but those backups can be pulled down and deleted from Storage once you're confident the rename fixes are stable.

## PART 3 — PRIORITIZED ACTION LIST

| # | Change | Type | Est. impact | Effort |
|---|---|---|---|---|
| 1 | `loadVerifiedUsers` → `onSnapshot` listener | reads | −1 to 2M reads/day | ~1h (3 examples exist) |
| 2 | Add 2–5s `_cache` to bonus-hunt-data, bankroll-data, slot-request-data, overlay-data | reads | large, per open overlay | ~1h |
| 3 | Slow overlay polls: 300/800ms → 1000–1500ms | reads | large | ~30m |
| 4 | Heartbeat 60s → 3–5min | writes | −~48k writes/day | ~5m |
| 5 | community rebuild 2min → 10min | reads | −~26k reads/day | ~5m |
| 6 | Clear `discordVerified` on the old holder when a Discord link moves | security | closes multi-account cert | ~20m |
| 7 | Optional stricter casino gate: require `underAffiliate` / match on `providerUid` | security | closes honour-system farming | ~1h |
| 8 | Pull + delete backup snapshots from Firebase Storage once rename fixes are stable | housekeeping | frees Storage bytes | ~10m |

**Recommended order:** 1 → 4 → 5 (cheapest big wins) → 2 → 3 (overlay work) → 6 → 7 (security hardening). Items 1–5 are pure infrastructure with zero user-visible change; 6–7 change giveaway-eligibility behaviour so they deserve a conscious decision, not a silent ship.

## Notes / caveats

- Read-cost estimates are order-of-magnitude, derived from loop cadence × fleet size × typical collection size. The exact split will be visible in Cloud Monitoring → Firestore per-collection read metrics; worth confirming the `verified_users` hypothesis there before/after the item-1 change to measure the actual win.
- This audit did not load-test or run anything against production. Every finding is from reading the current committed code.
- Nothing in this file has been implemented. It is a backlog, companion to `TODOS.md`.
